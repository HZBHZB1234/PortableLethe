## 2. Rust catalog v2 解析器（难点 1，需自研）

依据工作区 `tools/parse_catalog.py` 文件头，格式如下（用 Rust 实现只读解析）：

```
header: magic i32 (0x0DE38942), version i32 (=2),
        KeysOffset, IdOffset, InstanceProviderOffset, SceneProviderOffset,
        InitObjectsArrayOffset, BuildResultHashOffset  (u32 each)

字符串编码(offset):
  0x80000000 -> UTF16
  0x40000000 -> 动态串：低 30 位为偏移，指向 (partOffset, nextOffset) 链表；
               version>1 时按分隔符逆序拼接（长 key 会被切段，故不能明文 grep）
  其他       -> 基本串：(offset-4) 处 i32 长度 + 数据

数组: (offset-4) 处 i32 字节长度，数据从 offset 开始
keys 区: u32 对 (keyOffset, locationListOffset)
location: 7 个 u32 [primaryKey, internalId, providerId, dependencies(array),
                      depHash(i32), data(DecodeV2), type]
```

**v1 实现范围**（最小可用）：
1. 解析 header + strings + keys + locations；
2. API：`find(prefix_or_regex) -> Vec<(key, internalId, bundleName)>`；
3. `bundle_name_from_internal_id()`（去掉 s-token 前缀与 `.bundle`）；
4. `extract_stoken(settings.json)`。

不做完整 `--chains` 递归展开（需要时再补）。产物模块 `hub-core/src/catalog.rs`，纯 Rust 无依赖（或仅 `regex`）。

风险：动态串拼接规则写错会导致 key 匹配漏报——用 `tools/parse_catalog.py --find "static_s1_0"` 的输出做对照测试。

## 3. unityfs Spike（本轮已完成，**通过**）

### 3.1 环境
- Rust `cargo 1.93.1` / `rustc 1.93.1`；Python 3.11.9 + UnityPy 1.25.4（仅作 ground truth）。
- 测试 bundle（真实游戏数据）：
  `SeedOfMirror-server/.local/.static-staging-953660f9/static_s1_0_assets_all_7061ce4fb64bbc9d5eb4d8a982a71418.bundle`（2,944,273 B）。

### 3.2 方法
1. UnityPy（设 `UnityPy.config.FALLBACK_UNITY_VERSION = "6000.3.12f1"`）提取全部 TextAsset → `_scratch/unityfs_gt_all/`。
2. Rust 项目 `_scratch/unityfs_spike/`（`unityfs = "0.1.4"`）：
   ```rust
   let bytes = std::fs::read(path)?;
   assert!(is_unity_bundle(&bytes));
   let paths = extract_unity_assets(&bytes, out)?;
   ```
3. 逐文件 SHA256 比对。

### 3.3 结果

| 指标 | 结果 |
|---|---|
| `is_unity_bundle` | true |
| unityfs 提取文件数 | **2185** |
| UnityPy TextAsset 数 | **2185** |
| 按基名匹配缺失 | **0** |
| SHA256 不一致 | **0** |
| 扩展名差异 | 42 个文件 unityfs 输出 `.txt`（UnityPy 为 `.json`）；按基名索引即可 |

**结论**：`unityfs 0.1.4` 可完全替代 UnityPy 做静态数据提取，且**不需要设置 Unity 版本回退**（无 UnityPy 的 fallback 警告）。Hub 侧只需在入库时把扩展名统一为 `.json`。

### 3.4 注意
- 该 bundle 来自工作区 staging 目录；接官服新版本 bundle 时需重跑一次对照。
- 42 个 `.txt` 的来源可能是 TextAsset 的 `m_PathName`/内容探测差异，不影响内容。

## 4. 同步算法（类别独立、整批原子）

```
1. 探版本：GET 官方 URL（HEAD/If-None-Match）→ 304 即结束
2. 读本地状态 resources/.state.json：{ source, etag, version, files: {path: sha256} }
3. 差异计算：新增/变化 → 下载队列；本地多出/官方 removed → 删除队列
4. 下载：hub/blobs/staging/...（.part 文件）
   - 支持 Range 续传（若 .part 存在）
   - 完成后校验 size + SHA256；失败重试 3 次（指数退避）
5. 原子切换：staging → 正式版本目录；写状态文件（tmp+rename）；
   更新 current junction；保留上一版目录用于回滚
6. 部署：
   - modfiles → 实例 MOD_FILES_DIR（立即生效）
   - staticdata → hub/resources/official/current，实例 static junction 已指向它；
     标记"需重启"并触发 /hub/request-restart
   - bundles → 写独立缓存目录（opt-in）
7. 失败语义：任一文件失败 = 该类别整批不切换；上一版保持可用；UI 显示具体原因
```

## 5. 静态数据目录契约

```
<STATIC_DATA_DIR>/
  StaticData/<原始官服目录结构>/*.json     # 2185 个 TextAsset，基名即逻辑名
  Localize/en/EN_Personalities.json
  Localize/en/EN_Skills*.json
  Localize/en/EN_SkillTag.json
```

- Hub 写入时按**基名**建索引（统一 `.json`），与服务端 `StaticData.OpenStream(logicalName)` 的查找规则一致。
- 服务端启动时若目录缺失/文件损坏：记录警告并跳过该数据；关键表缺失给出醒目告警但不阻止启动。
- Hub 更新静态数据必须触发服务端重启（类型初始化缓存）。

## 6. bundle 差异同步（Rust 版 sync_server_bundles.py）

已验证的既有逻辑（`tools/sync_server_bundles.py` 头注释）：
- 两服 catalog 绝大多数 bundle 名称+缓存键一致 → 共享；
- 少量独有 bundle → 只同步差异；
- CDN 需要请求头 `X-Requested-With: this_is_header_value`；
- 缓存布局 `<CACHE_ROOT>/<外层 32hex>/<内层 32hex>/__data`，内层 = bundle 文件名尾段 32-hex（内容 hash），外层来自 catalog；
- `--keep-other` 保留两服差异 bundle，切换零重下载但占空间（**同机模式默认开启**）。

Rust 实现复用第 2 节的 catalog 解析器 + `twox-hash`（xxhash64，seed 0，格式 `{:016x}`）+ `reqwest`。

## 8. 验收标准

1. Rust catalog 解析器对 `static_s1_0` / `userticket` 的查找结果与 `parse_catalog.py --find` 一致；
2. unityfs 提取 + 官方目录镜像后，服务端重启能读到 2185 个静态表；
3. modfiles 同步无需重启即被服务端提供；
4. bundle 差异同步在同机模式下不重复下载公共 bundle；
5. 任一类别同步失败可回滚到上一版，状态文件不损坏。
